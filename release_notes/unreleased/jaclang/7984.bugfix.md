- **Fix: native lowering of class-form enums and function-body imports**: Two constructs the native backend rejected now lower. (1) A Python-class-form enum (`class C(StrEnum)` / `class C(IntEnum)`, as opposed to a Jac `enum`) was registered as an ordinary struct archetype, because both `LayoutPass._build_enum_layouts` and `NaIRGenPass._register_enums` key on `uni.Enum` declarations; member reads (`C.MEMBER`) and `.value` had no lowering, so a `__str__` returning `self.value` demoted to Python (this is what took `Constants.__str__` out of the sealed front end). Such an enum is now lowered as the underlying scalar it is on the server pathway: a `StrEnum` member is its string and an `IntEnum` member is its int, so members, `.value`, `.name`, `str()`, f-string interpolation and string comparison all match the server result, and the dunder stays native. Members whose value is not a literal (an `IntFlag` written with shifts, say) are unchanged and still diagnosed rather than lowered to a wrong constant. (2) An `import` written inside a function or method body raised "Native lowering failed for statement 'Import'" plus a cascade for every name it bound, even though module-level imports lowered fine; body-scoped imports are the house idiom for lazy and conditional imports. Import-driven registration now walks nested imports as well as module-level ones, and the statement itself lowers to nothing because a native binary has no runtime import step. An unsupported (Python-only) module imported inside a body earns the same `E5090` with the same guidance a module-level one already earned, at check time as well as at codegen.
