- **Scale: revision based rollback and a bundle retention contract**: a deploy already leaves a complete rollback target in the cluster, since the pod image is constant across versions and deploy patches rather than recreates, but nothing exposed or protected it. `revision_history_limit` is now a declared `KubernetesConfig` field that lands on every Deployment, defaulting to the 10 the API already applied, so rollback depth is something a consumer can read back instead of inferring. `list_revisions` reports an app's releases, grouped by the bundle digest that identifies them, because a Kubernetes revision number is per Deployment and a service whose pod template did not change takes no new revision. `rollback_to` reverts every service of a release to whichever revision carried it, and refuses when any of them no longer has one, rather than half reverting an app onto two versions at once. Both are scoped to the app's own deployments, so a namespace shared with another jac-scale app is never touched. `bundle_keys_from_pod_spec` and `referenced_bundle_keys` give consumers the retention contract that a bundle referenced by a retained revision is never deleted, reading the keys back out of the init container the injector itself builds so the writer and the reader cannot drift.
