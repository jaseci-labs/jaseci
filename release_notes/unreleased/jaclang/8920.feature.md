- **Workspaces: one repo declares many apps in `[apps.<name>]` tables and type-checks as one codebase (#8823)**: a `jac.toml` can now declare a fullstack web app, a mobUI React Native app, a CLI, and service apps side by side, each with a `kind`, a directory or file root, and optional `platform` and `route`; everything outside an app root is shared code. Membership is path containment, a file-rooted app claims exactly its entry file, and a toml with no `[apps]` table is one implicit app whose config is unchanged. The kind is the whole client story: `web-app`, `web-static` and `desktop` render the DOM, `mobile` is a React Native mobUI app, and `--platform` (android, ios, or web for a react-native-web build in the browser) is the only per-run override. Per-app config overlays any section under `[apps.<name>.<section>]` and merges base → app → profile → `jac.local.toml`, `${VAR}` interpolation now applies to every string in the file, and `[project] default-app` picks the app a bare `jac run` means. `jac run <app>`, `jac build <app>` / `--all`, `jac test <app>`, `jac setup <app>`, and `jac create --app <name> --kind <kind>` take the app name as the positional; `jac run --show` prints one plan row per app. `jac check` with no paths is the workspace gate: one rooted program per app, and a shared module is checked once under every app that reaches it, so a mobUI-illegal `<div>` in shared code fails under the mobile app and passes under the CLI in the same run; the language server does the same for an open shared file. The compiler learns about apps only through driver-stamped facts (`Module.app`, `app_root`, `app_kind`, `owner_app`), which enforce two new laws -- an app may not import another app's internals (E2039/W2039) and shared code may not depend on app modules (E2040/W2040) -- and a `.native.jac` variant must now agree with its base module's public surface (E5105) instead of failing at runtime on one platform.
- **Service apps replace the routes table, and the app boundary is structural**: a microservice is an app whose consumers are other apps. One cross-app import rule classifies every import as local, a client bridge, a service bridge, or a native binding; the three previous predicates and the routes-table service cut are gone. A cross-app import always compiles and type-checks as a cut -- service stubs are `async` and keyed by the owning app, every bridged symbol is coroutine-returning so a missing `await` is E1042 in every profile, and a non-bridgeable item is E5106 -- while whether the provider runs in-process, as a local fleet, or as pods is configuration (`[scale.gateway] colocate`, `jac run --fleet`, deploy always a fleet). A shared module that carries walkers or node/edge archetypes has exactly one owner (a file-rooted service app, the sole serving app, or `[project] default-app` when several apps serve); two serving apps with no default app and no explicit owner is E5107, and an app dependency cycle is E5104. Consistency is ACID within an app per request and eventual across apps: an un-awaited cross-app spawn goes through a transactional outbox with at-least-once delivery and idempotency keys honored by the receiving endpoint, and an awaited one raises a `BridgeError` family (`BridgeUnavailable`, `BridgeTimeout`, `BridgeRejected`) on both the server and `@jac/runtime`. Out-of-process consumers such as a CLI authenticate with `JAC_BRIDGE_TOKEN`. The jaclang.org example ships as the reference workspace (`core/`, `web/`, `mobile/`, `cli/`, two service apps) and is what `jac create --awesome` scaffolds; the mobile and service scaffolds for `jac create --app` are new.
