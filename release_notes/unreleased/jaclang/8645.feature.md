- **Feature: a base's own call reaches an importer's override, and the fused native prefix moves to seat two**: The native backend devirtualized a call a base class makes on `self` whenever no subclass in the *current module's* layout registry overrode the callee. An importing module's subclass is not in that registry, so every overridable method of every imported class bound statically to the base body and the override never ran. The vtables were correct and the slot held the right pointer; only the call site was wrong, and nothing diagnosed it: a two-module program printed one answer under CPython and another as a native binary while still exiting 0. Devirtualization now applies only to a module-private archetype, the one case a single module's registry can answer completely, and every other class dispatches through the vtable slot it already carries. That was the bug pinning the zero-bytecode crossing at one seat: `UniPass.transform` calls `self.before_pass()`, `SymTabBuildPass.before_pass` is the override that creates the pass's scope stack, and bound to the empty base body (which LLVM then inlined away) the stack stayed null and the crossing segfaulted reading it. `PREFIX_NATIVE_FRONTIER` moves to 2 and `SymTabBuildPass` now executes inside the crossing, reading no driver-stamped fact, so the `codespace-pinned` clause still keeps a pinned module out entirely. The seal's parity canary grew to match: it compared only what a parse produces, which no table pass writes, so it now also compares each scope's name set, overload and implicit-rebind keys, `kid_scope` fan-out and parenting, plus every name atom's symbol identity with its defn and use counts. A base that earns no vtable at all in its own module still binds statically for an importer that subclasses it; that is a per-module `needs_vtable` answer to the same cross-module question, it moves object headers rather than call sites, and it is tracked separately.
