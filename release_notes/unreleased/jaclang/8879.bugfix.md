- **Fix: `jac run` on a web-app keeps its dev server, and local microservice mode finally serves the web app**: declaring `[scale.microservices.routes]` describes the service cut a project wants when it is *deployed*, but it also silently decided the local topology, so `jac run` on a web-app traded the vite dev server for a gateway that served no site at all: `/`, `/docs/...` and `/walker/...` 404'd, `/cl/app` was raced across every service in registration order (a service still compiling hung the page), `[serve] base_route_app` was ignored, and nothing built or served a client. The only escape was `[scale.microservices] enabled = false`, which a deprecation warning told you to delete. Asking for the topology is now explicit: `jac run --ms` (or `[scale.microservices] enabled = true`) selects local microservice mode, `--no-ms` (or `enabled = false`) forces one process, and a dev-client run defaults to one process while `jac run --serve` and every deployed path keep the gateway when routes exist. The gateway now knows which service is the app -- the entry module's, the one `ensure_main_service` already synthesizes -- and gives it the project root: `/`, `/cl/<page>`, `/static/client.js` and unclaimed client routes are forwarded to it instead of 404ing or being probed across the fleet, replicated families prefer it, and it runs exactly as the single-process server does (vite plus HMR under `--ms`, its built bundle under `--serve`), so `[serve] base_route_app` is honored where it always was. Boot no longer loses routes either: services start in parallel instead of one 60-second `/healthz` wait at a time, a service that is still compiling stays `starting` rather than being written off as unhealthy and dropped from routing, and its `/openapi.json` answer is never cached until it is healthy, so its routes are learned on the first request after it can publish them rather than being missed for the whole `route_refresh_seconds` window. The gateway also stopped building the admin console from source before it binds: a local project has no staged console, so every start paid minutes for a build nobody asked for, and running it alongside the app's dev server was enough to take that dev server down; `/admin` builds on its first request, as it already did on the single-server path. A bodiless status is also framed as one: the server used to answer a 304 or 204 with `Transfer-Encoding: chunked`, which a browser rejects outright (ERR_INVALID_HTTP_RESPONSE), so every revalidated module the gateway proxied from a dev server failed to load. In dev the gateway keeps two addresses for the app service -- its API for health, spec and walker traffic, its vite dev server for pages -- so a client dev server that dies costs HMR, not the site.
