- **Breaking: `jac start` and `jac dev` fold into `jac run`, and the project kind decides execute-vs-serve for a named file too**: `run` and `start` were already one command wearing two names. `jac run` with no filename resolved the project kind and dispatched `execute` / `serve` / `build`, so a bare `jac run` in a `web-app` already served; `jac run app.jab` already served servable kinds; and `jac dev` was three lines ending in `start(dev=True)`. What the verb still decided by itself was the codespace: `start` called `set_effective_default_codespace('server')` before importing while `run` read `[build] default_codespace`, so the word you typed, not the project, chose the stratum. The verb no longer decides anything. `start` and `dev` are tombstoned (`jac run --serve [--port N] <file>`, `jac run --dev`), and `run` carries the serve surface: `--serve` / `--no-serve`, `--port`, `--dev`, `--api-port`, `--no-client`, `--faux`, `--client`, `--host`, `--platform`, `--takeover`. The visible-verb budget drops from 28 to 26. **A named file now resolves the kind as well**, closing an asymmetry that predates the merge: in a `service` or `web-app` project `jac run` served but `jac run main.jac` ran the same project as a script, and both now serve. Building stays a bare-`jac run` action: in an artifact kind (`native-binary`, `py-package`, `mobile`, ...) the artifact is the project rather than the file, so `jac run main.jac` there executes the file as it always did and only a bare `jac run` builds. `--serve` and `--dev` are sibling action selectors: `--serve` asks for a plain serve and does not inherit a kind's `dev` default (so `jac run --serve` on a `web-app` matches the old `jac start`, not `jac dev`), while other kind properties such as a `service`'s `no_client` still apply. `--serve` forces serving where the kind executes (the replacement for `jac start <file>` outside a servable project), `--no-serve` forces the reverse. A cross-mode flag is a hard error rather than a silent no-op: `--port` against a `cli` kind, or `--entry` against a kind that serves, names the flag and the kind and exits 1. A `[serve] port` bridged from jac.toml is not read as a typed `--port`, so it neither forces the serve path nor trips that error. **Serve flags must now precede the filename**, because `run` carries a `REMAINDER` for script arguments: `jac start app.jac --port 3000` becomes `jac run --port 3000 app.jac`, and a flag written after the file is passed to the script instead. `--api_port` is spelled `--api-port`, matching every other hyphenated flag. The deploy flags leave the serve path entirely: `--scale`, `--target`, `--enable-tls`, `--dry-run` and `--show-yaml` become `jac scale deploy [app.jac] [--target T] [--enable-tls] [--dry-run] [--show-yaml]`, which deploys the project's `[project] entry-point` when given no file. `scale_start()` splits accordingly into `scale_local_serve()` (the local-microservice autodetect, still on every serve) and `scale_deploy()` (the Kubernetes realizer, reachable only from `jac scale deploy`), so microservice mode no longer has a `--scale` flag to dodge. The `enter()` function is deleted and its body inlined into `run`'s execute path; `--entry`, `--node` and `--root` are unchanged. Sibling-service spawning and the Kubernetes pod entrypoint follow the new spelling: `headless_start_args` emits `run --serve --port <p> --no-client <file>` and the pod runs `exec jac run --serve`. One caller is deliberately left behind: the `happy-path` workflow installs the published binary on a bare machine and never checks the tree out, so it still says `jac start` and must become `jac run --serve` when a release carries this change (the tombstone names that spelling, so the first nightly failure after the release says what to do).
