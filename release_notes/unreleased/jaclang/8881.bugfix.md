- **Fix: an unresolvable relative import is a compile error, and a base-less `.test.jac` module is analyzed**: two ways a compile-time mistake reached the browser instead. A relative import whose target file does not exist (`import from .label { Label }` with no `label.jac` beside it) only warned `W1100`; boundary classification could not see a client module behind the unresolvable path, so it left the import statement in the server codespace and the ECMAScript backend, which emits only client statements, dropped it, publishing a bundle whose binding had vanished and which failed as `ReferenceError: Label is not defined` at runtime. A relative import names a file inside the author's own project, so an unresolvable one is now `E1134`, naming the import and the file that carries it; bare specifiers keep warning (they can name an npm package installed later), and `import type` and comptime imports are untouched. Separately, the compile driver skipped the entire analysis schedule for any file that was annex-shaped (`.impl.jac` / `.test.jac`), on the assumption that an annex is always woven into a base module analyzed in its place. A `.test.jac` with no base module beside it is itself the compilation unit, and it was compiled with no type inference at all: every `Expr.type` stayed `None` and the checker never stamped `FuncCall.call_kind`, so the client backend emitted an archetype constructor as a plain call (`TestClient()`, which JavaScript refuses without `new`) and left the `jid()` builtin un-lowered. Analysis is now skipped only for an annex that actually has a base module to be analyzed with. The jac-shadcn registry's component templates carried the same shape on purpose -- a `import from ...lib.utils { cn }` placeholder that `jac shadcn add` rewrites to the destination project's own utils module -- so the registry now ships the `lib/utils.jac` that placeholder names, and `jac shadcn init` writes the destination copy from it instead of from a second inline copy of the same source.
