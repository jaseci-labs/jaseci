- **Fix: which identity stack owns `/user/*` is now a configuration decision, the core server stores scrypt, and a dev server keeps its signing secret**: the owner of the identity endpoints was a side effect of an import. `get_api_server_class` asked the scale plugin for a server class and answered any `ImportError` in that graph with a DEBUG line and `None`, which demoted the whole API server to the core class. The two classes own different credential stores -- Postgres holding `scrypt$` hashes, and sqlite `.jac/data/main.db` holding unsalted sha256 -- so one transient compile error or half-written cache entry moved `/user/*` to a store with none of the existing rows in it, and every account created before the flip was told its password was wrong while its graph data sat untouched. `identity_owner()` now resolves the owner from configuration alone: `JAC_IDENTITY_BACKEND`, else jac.toml `[serve] identity`, else `auto`, which is the scale identity when the scale stack is configured for the project (a `[scale.database]` url, or `JAC_DB_URL` / `JAC_SCALE_RUNTIME` in the environment) and the core identity when it is not -- the same predicate the scale runtime already used, so the two can no longer disagree. It is resolved for the project being served rather than for the directory the command was typed in, so `jac run inner/app.jac` from a parent directory honours the inner project's setting; a value it does not recognize, or a `jac.toml` it cannot read, is refused rather than guessed; and a scale stack that will not import raises with the module name instead of quietly serving the other store. The core server also stopped writing unsalted sha256: signup, login, and password change go through the shared `authcrypt` module, and both stacks accept a legacy sha256 row once and rewrite it as scrypt on that login, so accounts written before the migration carry across without a reset. Separately, `[scale.jwt] secret` no longer defaults to a literal shipped to every project: a dev server mints one into `.jac/data/jwt_secret` (gitignored, 0600, following `JAC_DATA_PATH` like the core store does), reads it back on later boots so sessions survive a restart, and refuses to sign at all rather than fall back to a secret one process keeps to itself. Importing the scale identity no longer mints that file as a side effect, so a core-identity project and an image build never create one.
- **Upgrade note: a multi-replica deployment that never set `[scale.jwt] secret`**: replicas used to share the shipped placeholder, which is public and therefore forgeable, and now each mints its own secret unless they share a data directory -- so tokens minted by one replica are rejected by another. Inside Kubernetes this is detected and the placeholder is kept with a warning at boot; anywhere else there is no runtime signal for it, and the boot log names the file it minted and says a deployment must set the key. Set `[scale.jwt] secret` before upgrading a deployment that has more than one replica.
