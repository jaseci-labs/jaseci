- **`del` now means the same thing under all three backends**: the client backend returned early on any attribute or subscript target without emitting anything, so `del d["k"]` and `del o.x` in a `cl` module were silent no-ops in the compiled JS, and its edge arm called a single-object disconnect that could not accept the array an `[edge ...]` query yields. The native backend matched only `del <edge name>` and fell off the end of its branch chain for every other shape, which is why `del (d[k], );` compiled to nothing; worse, `del L[i:j]` lowered to a single `del_at(i)` and `del L[::2]` was dropped, so both returned a wrong answer instead of refusing. All three now classify the target the same way. The client backend splices arrays (a raw JS `delete` would leave a hole), carries a slice's step through, and destroys through a new OSP `osp_destroy`; the native backend lowers attribute and subscript targets through the deleter accessor and the dict/list primitives, destroys names and value targets, and reports `E5092` for a slice it cannot lower rather than mis-lowering it. A differential harness in the test suite now runs every Python-legal `del` form through both Jac and CPython and asserts they agree, and a parity test JIT-compiles the same graph program natively and checks the counts match the Python backend.
