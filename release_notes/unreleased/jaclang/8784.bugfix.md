- **Fix: Type-only imports are checked instead of emitting a dead ESM specifier**: Import bindings now carry a kind (value / type / both) inherited from whatever they resolve to, and the checker asks whether the backend lowering the importing module leaves a runtime binding for the name. A TypeScript `interface` or `type` alias in a `.d.ts` has no runtime export in any codespace, and a jac `type` alias has none in client code, so a plain `import from` of either used to pass `jac check` silently and then emit a named specifier the browser refuses at link time, taking the whole client module graph down with no diagnostic upstream. Two new blocking errors replace the silence: `E1131` when such a name is reached by a plain import (move it to `import type from <module> { Name }`), and `E1132` when an `import type` binding is used in value position (a call, an attribute read, an `isinstance` argument, a decorator, a base class, an assignment) on either backend. A jac `type` alias keeps its runtime binding on the server, so a plain import of one from server code -- including cross-module brand construction, `import from brands { UserId }` then `UserId(raw)` -- stays correct. Annotations, `has` field types, generic arguments, `as` casts and `type` alias right-hand sides stay legal everywhere. See [Type-Only Imports](../../reference/language/types-and-values.md#type-only-imports-import-type).
