- **Deploys no longer inherit the deploying process's microservices config** (#7874): an app deployed in-process by a host that is itself a jac-scale app (the SDK's `ScaleClient` path, e.g. a builder service deploying user apps) could pick up the *host's* `[scale.microservices]` when it declared none of its own. `ManifestBuilder` and `KubernetesTarget` treated an explicitly empty config as "nothing supplied" and fell back to the process-global `get_scale_config()`, so the host's `shared_volumes` became PVCs in the guest's namespace - and where the host's volume name was an unresolved `${VAR}` placeholder, the literal `${...}` reached the API server and the deploy died with an opaque 422. The config is now a true sentinel: an omitted config still falls back to the loaded one (the CLI path), while a supplied config is honored exactly, empty or not. The `JAC_SV_ROUTES` environment fallback in `normalize_microservices_config` is likewise gated to the pod runtime that needs it, so a caller-supplied config can no longer take routes from the host's environment. This restores the SDK's documented guarantee that a programmatic deploy is driven entirely by its `DeploySpec`. Independently, `k8s_safe_name` now enforces RFC 1123 rather than only lowercasing and swapping underscores: it strips characters outside `[a-z0-9.-]`, trims to a leading and trailing alphanumeric, caps at 253, raises on a name with nothing usable left, and rejects an unresolved `${...}` placeholder outright instead of quietly sanitizing it into a plausible-looking volume name.
