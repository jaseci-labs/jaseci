- **byLLM: per-call usage during a streaming ReAct loop (`usage_step`)**: a new `usage_step` `StreamEvent` fires once per individual LLM call in a `stream=True, logging=True` tool-calling invocation — the main ReAct iteration, the final-answer restream, and the recovery call all get their own event, shaped identically to the existing `usage` event so both can be parsed with the same code. Previously usage was only visible once, in a single aggregate after the entire invocation finished, so a caller enforcing a per-turn budget could only discover an overrun after the whole (possibly many-call) turn had already run. Correctly attributes usage when auto-compaction interleaves with a react-loop call in the same iteration, rather than reporting only the last recorded entry. `IterationContext` (used by the existing `on_iteration` hook) also gains `total_cost`, the real cumulative cost across completed calls, alongside the existing `total_tokens`.
- **byLLM: `llm_timing` no longer duplicates token counts**: `llm_timing` (an undocumented `StreamEvent`) previously carried `completion_tokens`, `prompt_tokens`, `cache_read_input_tokens`, and `cache_creation_input_tokens` alongside its `duration_ms`/`iteration` timing data. Now that `usage_step` covers the same numbers per call (plus `cost`, `total_tokens`, and `call_kind`), `llm_timing` carries only `duration_ms`/`iteration` — a behavior change for any code reading those fields directly off `llm_timing`, since they were never part of a documented contract.
- **byLLM: `cache_read_input_tokens`/`cache_creation_input_tokens` are now consistent across providers**: providers report prompt-cache usage differently — Anthropic and Gemini set it as a top-level field, OpenAI only nests it under `prompt_tokens_details.cached_tokens`, and some providers have no cache-creation concept at all. Every recorded call now normalizes both fields to the same names regardless of provider, defaulting to `0` when not applicable instead of being silently absent. Applies to `usage`, `usage_step`, and the `tokens` telemetry field alike, since all three share the same underlying record.
- **byLLM: tool-calling ReAct calls now get litellm's native cost too**: `include_cost_in_streaming_usage` only attaches a cost when litellm rebuilds a full response from streamed chunks with a `logging_obj` attached - byLLM's own reconstruction inside `dispatch_streaming_with_tools` (needed to parse tool calls out of the stream) wasn't passing one, so every ReAct-loop call was silently falling back to byLLM's manual `completion_cost()` computation regardless of the flag. Now passes the stream's own `logging_obj` through, so ReAct-loop calls get the same native cost the plain no-tools streaming path already had. `_attach_call_cost`'s fallback still fires correctly wherever no native cost is available (non-streaming calls; unchanged).
