- **The fixed-width JSON wire form is one rule on both lanes, and sized arithmetic on the server lane costs an order of magnitude less** (#8601, follow-up to #8544): an `i64`/`u64` value now leaves the server as a JSON string when it falls outside the safe-integer range (`abs(v) > 2**53 - 1`) and as a JSON number otherwise, which is what the client lane already did; both decoders accept either form, so a 64-bit field round-trips between the lanes without losing precision. **Breaking:** an HTTP consumer reading a large `i64`/`u64` field from a walker or `def:pub` response now sees a JSON string where it used to see a number (values within the safe range are unchanged, as are plain `int` fields and every narrower width). Alongside: the client runtime no longer installs a `BigInt.prototype.toJSON` patch on the page, encoding through `_jac.fw.stringify` instead, so other libraries keep the standard `JSON.stringify` behaviour for `BigInt`; widths below 64 bits compute in JS numbers rather than `BigInt` on the client; the server-side scalar table is memoized, which takes sized arithmetic there from roughly 860x plain `int` to roughly 60x; and `T.MIN % -1` returns `0` natively instead of faulting the process (only the quotient of `T.MIN // -1` leaves the range).
