- **A client state setter is a real binding again, and an emitted module can no longer name what it never binds** (#8224): `has X` inside a client function names two things, the value and `setX`, and returning both from a hook is the ordinary React shape. The read-your-writes migration replaced the `useState` destructure with a store cell and kept every *write site* working by rewriting it, but a setter handed to a component, stored in an object, or returned from a hook has no site to rewrite: it fell through to a bare identifier. `jac check` passed, `jac build` exited 0, and the page died on load with `ReferenceError: setTheme is not defined`. The React family now binds `setX` to the cell's setter, which the cell closes over rather than reaching through `this`, so the setter keeps the stable identity `useState` gave it and dependency arrays and memo boundaries do not churn; Preact inherits it and Solid's signal destructure is unchanged. `setX` is also registered as a synthesized symbol typed `Callable[[T], None]`, so the checker resolves and type-checks setter references instead of leaving the name to codegen's memory, and each backend owes a binding for a name the language admits exists. Behind both, client codegen now audits the module it just emitted: every identifier it references must resolve to a declaration, an import, a parameter, or the ambient browser surface, read from the same stubs `jac check` resolves client-tier names against. Anything left is `E5101`, naming the Jac source line. That is the general form of a failure that had already shipped twice from this pass -- #8072 was a server endpoint referenced as a value and never emitted -- and it caught two unbound names in a test fixture on its first run. Requiring declared ambient globals in client code, so a truly unbound name becomes a check-time error rather than resting on a curated allowlist, is tracked separately.
