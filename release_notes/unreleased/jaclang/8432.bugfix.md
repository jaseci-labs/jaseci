- **TypeCheck: comparing a variable to a string literal narrows it, the way comparing to a number always has** (issue #7261): `if v == "node" { ... }` with `v: str | None` left `v` as `str | NoneType` inside the guard, so using it there reported `E1001: Cannot assign str | NoneType to str` even though `v` could only be `"node"` at that point. The same guard written against `5`, `1.5` or `True` narrowed correctly, which made the failure look like it came from somewhere else, and the usual workaround was an `is not None` check next to a comparison that had already ruled `None` out. Every spelling of a literal now narrows alike: a plain `"node"`, an implicit concatenation `"no" "de"`, a parenthesized literal, in `if` and in a ternary. An f-string with an interpolation is not a fixed value and still does not narrow.
- **TypeCheck: ruling a value out with `!=` no longer rules out its whole type** (issue #7261): `if v != 5 { ... }` with `v: int | None` typed `v` as `NoneType` inside the guard, over a value that was really an `int`. The check passed, then the same code failed to build natively and fell back to Python (`E5092`, binding a void-typed value); where it did compile, `int` operations inside the guard reported errors against a type the variable did not have. Ruling out one value never rules out the rest, so `v` now keeps `int | None` there, and the same holds on the `else` branch of `==`. Where the alternatives really are spelled out the narrowing still applies: `v: Literal["a"] | None` with `v != "a"` is `None`, and `Literal["a"] | Literal["b"] | None` keeps `Literal["b"] | None`.
